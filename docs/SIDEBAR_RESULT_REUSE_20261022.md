# 侧栏完整交互链审计与结果卡复用 · 2026-10-22

用户反馈上一版仍卡顿。本轮从点击、搜索、结果提交、导航投影、布局、事件绑定和关闭释放整条链路继续审计。保持既有属性展开、固定导航目录、桌面鼠标交互和移动端行为；本版仍为开发候选，未晋升冻结基线。

## 主要发现

此前减少左侧目录的重复写入后，剩余耗时主要集中在右侧 `renderPage`：即使返回刚看过的目录，也逐张重建标题、标签、属性、图标和控件事件，再触发无障碍名称处理。已有虚拟窗口限制挂载数量，但没有复用不同次筛选之间的结果卡。

本轮新增内部 `browse-card-reuse.js`，由现有 ResultRenderer 的 `renderPage` 调用。仅桌面 sidebar 的普通浏览启用：

- 每个窗口最多保留 96 张结果卡，使用现有结果对象；没有第二套文件索引或搜索结果状态。
- 命中同时要求原结果对象、可见内容指纹与显示配置一致。摘要/属性原地变化也会失效；显示字段、排序偏好、文件夹颜色和跨年时间格式都参与校验。
- 点击仍同步计算真实结果。复用卡片更新位置和末行状态；名称打开、属性 Picker、筛选及排序继续由原 Owner 处理。
- 先用占位节点暂存复用位置，所有新卡构建成功后才移动原节点。构建中途或提交后异常都能恢复完整旧页面及节点位置。
- 查询、打开中的 Picker、批量模式、展开的动作栏、外部单选和其他宿主使用原构建路径。使用过动作栏或展开长属性值的卡片不直接复用。
- 缓存有数量上限，关闭窗口释放。首次访问且未命中的结果仍需正常构建；不通过延迟提交或吞掉连续点击减少工作。

运行差异仅为 `page-and-snippets-methods.js`、Renderer 的销毁清理，以及新内部模块；未修改 CSS、弹窗位置、焦点 API、公开接口、manifest 或 data。

## 测量

通过 Chromium 和模拟 Obsidian 的真实 SearchView 生命周期，执行鼠标输入；CPU 放慢至 4 倍。每组包含 40 次分组折叠点击及 50 次目录点击，并检查滚动覆盖和键盘跳转。旧版来自父提交，先运行旧→新，再运行新→旧；下表耗时是两次测量合并后的 `Navigator.select` 同步处理时间，不包含所有后续绘制，也不是原生 Obsidian 的输入延迟。

| 文件数 | 每轮卡片构建：旧→新 | 平均同步点击：旧→新 | P95：旧→新 |
|---|---:|---:|---:|
| 161 | 760 → 74 | 42.98 → 20.36 ms | 58.30 → 47.70 ms |
| 2400 | 640 → 56 | 39.29 → 20.95 ms | 48.90 → 39.10 ms |

平均同步处理耗时分别减少 52.6% 和 46.7%。两种运行顺序均重现卡片构建数量下降，所有点击送达、筛选一致性、滚动覆盖和键盘跳转检查通过。另一个预热双目录场景中，10 次切换由重建 120 张卡变为 0 张，每次仍恰好搜索一次。

首次打开未缓存的目录仍有构建成本；这些结果不能证明每帧都在 16 ms 内，也不等于全部卡顿已经消失。
