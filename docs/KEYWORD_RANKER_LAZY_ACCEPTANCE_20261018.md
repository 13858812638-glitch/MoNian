# GLS v5.2 · 关键词匹配按需计算 v1 候选 · 验收与性能报告

**状态：仅为性能优化开发候选，尚未正式冻结。** 当前唯一正式冻结基线为 **GLS v5.2「Picker 模式单次绘制 v1」**（2026-10-18）。本轮严格从其完整正式 Source 的 `src/` 派生，禁止反向覆盖正式版。

## 本轮范围与根因

- 发现 8,000 个模拟文件的新关键词搜索中，首次标题命中查询 `performSearch` 同步耗时约 **76.1 ms**，其中 `_rankCandidates` **63.8 ms**，而结果列表仅挂载约 **18** 张卡片。可见当时主要热点是匹配与排序，不是虚拟列表全量绘制。
- 原 `src/features/search/ResultRanker.js` 在判断标题直接命中（tier 1、2）之前，已计算所有词项标题/标签匹配、标签规范化和文件类型，很多计算在提前返回时根本不会使用。
- 修改为：先处理精确标题与连续标题命中，再在需要时计算多词标题命中、文件类型与标签集合。`tier` 判定顺序、排序结果、标题匹配范围、正文通道、搜索条件和业务筛选逻辑保持不变。
- **运行源码仅变动 1 个文件：`src/features/search/ResultRanker.js`；JS 模块 146、静态依赖边 635，不添加事件、状态 Owner、缓存、常驻监听、定时器或兼容层；CSS 与正式基线字节相同。**

## 模拟性能结果（同环境，非 iPhone）

| 场景 | 正式基线 | 候选版 | 结果 |
|---|---:|---:|---|
| 8,000 文件首次标题查询 `performSearch` | 76.1 ms | 41.1 ms | 约减少 **46.0%** |
| 同查询 `_rankCandidates` | 63.8 ms | 26.7 ms | 匹配排序明显提速 |
| 同查询虚拟列表挂载卡片 | 18 | 18 | 未改动 |

上述端到端数据为**分别启动的模拟 Chromium 页面中的单次同步采样**，不具备正式统计意义的 P95 或 iPhone 实机代表性；效果对标题直接命中查询最明显。无命中查询约 **48.5 → 50.7 ms**，没有观察到加速，不承诺所有搜索更快；索引构建和其他昂贵路径没有优化。

隔离的 8,000 文件匹配器 A/B 还对 15 类查询进行了多轮采样，标题高命中查询的匹配排序 P50 在该环境中由约 **65.3 → 23.3 ms**。这是独立的匹配器 what-if 试验，**不能与整个搜索流程的 76.1 → 41.1 ms 混为同一个指标**。

- 正式版与候选版的**实际构建产物**：300 模拟文件，桌面/移动端各 26 种查询，共 **52/52** 完整结果数组、tier、匹配范围、结果卡片一致。
- 8,000 文件、8 个代表性查询：**8/8** 输出计数、首尾样本、挂载卡片以及两组 32-bit 校验值一致（仅校验签名，**不是完整逐字节输出的证明**）。原拟运行的 8,000 文件全量 26 项由于执行时长中断，未声称通过。
- `npm run check`：PASS（146 模块 / 635 依赖 / 无未解析与循环引用）；`npm run build`：PASS；`npm test`：**134/134** PASS。
- 当前版 Chromium 桌面+移动业务流程：**40/40**；移动侧栏：**96/96**；导航精筛：**76/76**；索引失败恢复：**7/7**；搜索条件：**144/144**；Picker 光标：**36/36**；焦点：**96/96**；Picker Portal 正式验收脚本：**48/48**。
- Picker 模式切换 300 文件重新审计：标签与属性 18 个受测转换均仅完整重绘一次，保留上一轮已正式冻结的改善。
- **历史测试债**：旧版 A/B 浏览器脚本的文件夹计数口径“2 对 6”问题依旧；一份非正式 Portal 旧重测脚本因错误假设 Popup 必须是 Picker 的子元素而报错，在未经修改的冻结版本同样报错。不能把这两套老脚本写成通过，也不应为了让旧断言通过而改变业务。
